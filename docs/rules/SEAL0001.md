# SEAL0001: Classes should be sealed, static, abstract, or marked unsealed

| Property | Value |
| --- | --- |
| **Rule ID** | SEAL0001 |
| **Title** | Classes should be sealed, static, abstract, or marked unsealed |
| **Category** | Design |
| **Severity** | Warning |
| **Enabled by default** | Yes |
| **Code fix** | Yes, adds `sealed` or an `unsealed` comment |
| **Applicable languages** | C# |

## Cause

A class is not `sealed`, `static`, `abstract`, or marked `unsealed`.

## Rule description

C# makes a class inheritable by default. SEAL0001 removes that default: every class that is neither `static` nor `abstract` must be explicitly `sealed` or marked `unsealed`.

### C# default

| | Not inheritable | Inheritable |
| --- | --- | --- |
| Not instantiable | `static` | `abstract` |
| Instantiable | `sealed` | default |

### Under SEAL0001

| | Not inheritable | Inheritable |
| --- | --- | --- |
| Not instantiable | `static` | `abstract` |
| Instantiable | `sealed` | `unsealed` (marked with a comment) |

Record classes, declared with `record` or `record class`, are classes and are covered by this rule. Structs (including `record struct`), interfaces, enums, and delegates are never flagged. Generated code is ignored, though a `partial` type with both generated and hand-written declarations is reported at its hand-written declaration. A `partial` type raises a single warning unless any part declares `sealed`, `static`, or `abstract`, or is marked `unsealed`.

## Configuration

The rule may be configured to apply only to classes with specific visibilities by setting `sealant.SEAL0001.visibilities` in `.editorconfig`.

For example, the following limits the rule to `public`, `protected`, and `protected internal` classes:

```ini
[*.cs]
sealant.SEAL0001.visibilities = public, protected, protected internal
```

Set the option to one or more of the following, separated by commas. Matching ignores case and spaces around each one.

- `public`
- `protected`
- `internal`
- `private`
- `protected internal`
- `private protected`
- `file`
- `all`

`file` matches file-local classes. `internal` does not match them, even though their declared accessibility is internal.

`all` is the default and may be used in a nested `.editorconfig` to override an inherited setting.

If an entry is not recognised, the rule falls back to `all`, so a mistake makes the rule report more, not less.

The option matches the declared visibility of the class, not its effective visibility through containing types. For example, a `public` class nested inside an `internal` class is treated as `public`.

The option is read for the file that contains the reported declaration. A partial class is reported at its first hand-written declaration, so the option for that file applies.

Limiting the rule by visibility makes it practical to adopt in an existing codebase, one visibility at a time. Set the option to a single visibility, then use Fix All with `Seal type` or `Mark as unsealed` to resolve every warning with that visibility. Repeat for the next visibility. For example, seal the `public` classes first, then mark the `internal` and `private` classes `unsealed`.

## How to fix violations

Choose the first of these that applies:

1. `static`, if the type has no instance members. This case belongs to [CA1052: Static holder types should be static or NotInheritable](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1052), so enable it and let its code fix apply the change. If CA1052 is not enabled, making the type static is still the right answer to SEAL0001.
2. `sealed`, unless the type is designed for inheritance. This is the default answer.
3. `abstract`, if the type does not need to be instantiated and there is reasonable certainty that it needs to stay inheritable. It is a first-class C# and .NET concept and a stronger signal than `unsealed`.
4. `unsealed`, if the type needs to stay instantiable and there is reasonable certainty that it needs to stay inheritable.

If the choice comes down to `abstract` or `unsealed`, first check whether inheritance is really needed at all. If not, redesign the type: extract an interface or use composition.

`Seal type` is the default fix; it adds `sealed` before `unsafe` or `partial` when either is present, otherwise as the last modifier.

The `Mark as unsealed` code fix adds an `// unsealed` comment at the start of the line containing the position where `sealed` would be inserted.

Both code fixes can fix multiple violations at once, all the way up to the whole solution.

## Example

The following code snippet shows a violation of SEAL0001:

```csharp
class Foo { }
```

The following code snippet fixes the violation by sealing the class:

```csharp
sealed class Foo { }
```

The following code snippet fixes the violation by marking the class `unsealed`:

```csharp
// unsealed
class Foo { }
```

## When to suppress warnings

Do not suppress an individual warning unless you are adopting the rule in an existing codebase. In that case, a suppression (preferably with a clarifying comment) may be used to record that the decision about one or more classes is still open. Once the decision is made, remove the suppression and [apply the corresponding fix](#how-to-fix-violations). The same approach may be used for several classes by suppressing the rule for a file, folder, or project.

Suppress the rule for a file, folder, or project when you cannot change the source, are not allowed to change it, or keep it identical to upstream.
